# A3 实测：准备队列的端到端收益

2026-11-15 完成一轮七组对照，每组预热50次、计时3000次，共21000次原模型 forward。
本轮没有观察到收益：off 最快；同样的 worker 数下，MPSC 比原加锁入口慢22%–37%。
这是单轮 pilot，尚未完成14轮平衡复测，不能推广为任意模型或生产吞吐结论。

## 对照条件与结果

所有组均为 Python3.14.6 free-threaded，导入框架后 GIL=false；Torch2.13.0、CANN9.1、
TQ1、CPU8–15、同一候选库 D894。模型仍为原版 DLRM，B128、26表、V1024、D16、
sparse=True、50850个原始 IDs，空表保留。源代码、权重、输入和精度的身份检查全部通过。

主性能测试只有**一个 Python 模型调用线程**，worker 是原生 C++ Prepare 线程。
它测的是同一 free-threaded 运行时内的调度方案，不是 GIL-on/off 对比，也不是多 Python
调用线程的吞吐对比。四 Python 调用线程另外通过了保序和正确性验证。

同worker数下，MPSC比mutex的中位延迟分别增加22.55%、22.26%、37.38%。

六个启用组的计时窗口都实际执行75000个 Prepare/Execute，另有54000次保守回退同步。

全部最终输出及中间层数值检查通过，最终输出最大绝对误差8.94e-8。

## 为什么 Prepare 有重叠，却没有变快

1. **当前负载没有入口锁竞争可消除。** 性能测试是单Python caller，旧submit_mu没有多生产者
   争用。MPSC仍要等publisher完整返回才让caller继续下一次提交，单caller无法积累多个待发布
   请求形成批量收益，却对每个合格算子增加一次caller与publisher之间的交接。
   实测MPSC4比mutex4慢37.38%，自愿上下文切换从1096增加到1742次/forward，CPU也增加36.44%。

2. **可并行的只是准备工作的一部分。** caller仍串行做资格审查、shape/stride快照和Storage
   保留；每个合格EmbeddingBag在domain和snapshot阶段各审查7个Tensor。25次查表约350次审查，
   SDK缓存命中也不会消除这些步骤。状态、统计、allocator及原PTA路径仍有锁。

3. **有很多同步边界。** 每个forward有25个准备任务及18次保守回退：Addmm6、BMM1、Cat2、
   Index1、Zero1、Relu5、Sigmoid1，以及原始空Embedding1。回退先排空FIFO再同步默认stream，
   因此Embedding与Interaction等阶段之间的重叠受限。每个合格任务还创建完成事件，并在
   retirement路径record/wait/destroy，完成前不返还额度。最终lease可能在release lane释放，
   不能直接把这些事件等待都说成consumer串行等待。

4. **原始off路径也已有流水重叠。** caller做cache/query时，原TQ1 consumer和设备可以执行
   前一个算子；新增workers并不是从完全串行变成并行。NPU仍沿原默认stream/FIFO执行。
   两种入口的冷态诊断均观察到4个Prepare跨度重叠，但这没有转化为本轮端到端收益。

这些源码机制与实测的延迟、CPU和上下文切换增长一致，支持“管理和同步成本超过准备重叠收益”
的解释。没有取得各阶段的独立时间分摊，不能把增加的耗时全部归给某一把锁或某一个同步调用。
本轮SDK query/cache-hit计数仍为null；缓存可能缩小可并行的query工作量，但不能声称已实测
warm阶段GetWorkspaceSize=0，也不能拿旧R33路径的缓存数据替代这一轮。
